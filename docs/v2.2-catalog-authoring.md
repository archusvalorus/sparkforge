# The ability catalog — how to add a card or a tier (v2.2, since J2/J3)

*The authored catalog is `Sparkforge/Catalog/ability-catalog.json`. The game loads it at startup (`AbilityCatalog.swift`); the effects live in `Sparkforge/Systems/AbilityBehaviors.swift`; the canon and the Card Atlas read the same file (`tools/v2.2-catalog/catalog_reader.py`). `UpgradeManager` defines no card any more.*

## A card = one JSON entry + one native behaviour

1. **Define it** in `ability-catalog.json`, in the `cards` list, at the position it should draft from (order is behaviour: the seeded shuffle, the capstone guarantee's parity and the gateway-pity tie-break all read the pool in order).

   ```json
   { "id": "v22_example", "name": "Example", "tree": "fire",
     "face": "What the selection card says (≤ 4 lines of 17)",
     "detail": "Optional: the full wording for the MORE chip / Codex / Atlas",
     "requires": ["fireUnlocked"],
     "behavior": "v22_example" }
   ```
   - `id` is permanent and unique; **never reuse a retired id** (`retired` list — old saves still hold them). Prefix new ids with the version (`v22_`).
   - `tree` is a portable key (`fire`, `shock`, `bleed`, `guard`, `void`, `chill`, `growth`, `neutral`); `secondaryTree` makes a dual-tag bridge.
   - Flags: `"signature": true`, `"capstone": true`, `"secret": true` (absent = false). One signature and one capstone per coloured tree is the design rule the harness checks (CA), not the loader.
   - Gates: `provides` / `requires` / `blockedBy` are capability keys from the top-level `capabilities` list (each must also be a case of `UpgradeManager.Capability`). A new capability is a Swift enum case first.
   - Copy is static text. Numbers in copy are typed by hand (ruling D2); keep them in step with the effect.

2. **Give it an effect** in `AbilityBehaviors.swift`, keyed by the entry's `behavior`:

   ```swift
   add("v22_example", [
       { stats in stats.fireDamageBonus += GameConfig.Fire.exampleBonus }
   ])
   ```
   - Numbers live in `GameConfig` (never a new literal in the closure — ruling D3).
   - A card may reuse an existing behaviour key (`"behavior": "neutral_1"`); a behaviour no card binds is an error.
   - A mechanic that does not exist yet is native work (scene, nodes, `PlayerStats`) plus tuning in `GameConfig` — the catalog entry alone cannot create it.

3. **Run the gates**: `sh tools/catalog-harness/run.sh` (the loader's `JS0` gate first, then the catalog checks; `JF2`/`JP4` will report the new card as a deviation from the legacy parity record — expected for new content, and the record is re-recorded only under a ruling: `--record-parity <dir>` refuses an existing directory without `--force`). Update `tools/catalog-expect.json` counts. Regenerate the canon (`python3 tools/generate-ability-canon.py`, after adding the card's sidecar entry) and the Atlas (`python3 tools/generate-card-atlas.py`).

## A tier = one more `tiers` entry + one more closure

```json
"tiers": [
  { "face": "+25% Fire damage." },
  { "face": "+50% Fire damage." },
  { "face": "+100% Fire damage.", "requires": ["someCapability"] }
]
```
- `tiers` is the whole ladder, tier 1 first; absent = a one-tier card; present = at least two entries. The base `face` stays (it is what the detail surfaces show); each tier's `face` is its rung line.
- A tier may carry its own `requires` / `provides` / `blockedBy` (never tier 1 — those are the card's).
- `name` per tier is all-or-none (Panda's ladder).
- The native side must have exactly as many closures as the file has tiers; the loader refuses a mismatch (`tierCountMismatch`). Closures are **deltas** — rungs add, never re-set.

## What the loader refuses (so you don't have to remember)

Unknown keys, empty text, a wrong schema version, an unknown tree or capability, a duplicate or retired id, a tier list of one, gates on tier 1, a partial set of tier names, a `behavior` nothing registers, a behaviour nothing binds, a tier-count mismatch, a synergy ladder that is not exactly 3 / 5 / 7, a secret card the scheduler does not expect, a missing card that native code names. Every problem is reported with its path and a sentence; the app shows the error screen and the harness stops at `JS0`. A repeated key inside one object is caught before that by `tools/v2.2-catalog/lint-catalog.py`.

## Worked demonstration

`python3 tools/v2.2-catalog/fixtures/demo-existing-behavior-card.py` adds a card bound to an existing behaviour to a *copy* of the catalog, shows the game's pool holding it with no Swift change, then shows the same card with an unregistered behaviour refused at the gate. The live catalog is never touched.

## Checks that keep the readers honest

- `python3 tools/v2.2-catalog/check-reader-parity.py` — the generators' reader equals the game's compiled pool, key for key.
- `python3 tools/generate-ability-canon.py --check docs/v2.1-ability-canon.md` — the canon matches the catalog, the sidecar and the expectations (its source-input fingerprint covers the authored file).
