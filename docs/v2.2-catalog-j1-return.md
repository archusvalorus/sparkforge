### Schema, as built

The shape proposed in J0 section 4, with these rules made exact:

- `tiers` is absent for a one-tier card and otherwise has at least two entries. Tier 1 carries no gates; a tier's `name` is given for every tier or for none.
- Every capability a card uses must appear in the top-level `capabilities` list and must be a case of `UpgradeManager.Capability`.
- `trees` must equal native code's eight trees in order, with `name` equal to `Tag.rawValue`.
- Each coloured tree lists synergy thresholds exactly 3, 5, 7. Neutral lists none.
- Unknown keys are rejected at every level.

## 3. The loader contract (D1)

`AbilityCatalog.load` either returns a catalog whose every card is bound to a native behaviour with the same tier count, or a `CatalogLoadFailure`. There is no third outcome: no default is filled in, no card is skipped.

**Thirty diagnostic codes**, each with the place in the file (index and card id) and a sentence saying what to change:

| Group | Codes |
|---|---|
| The document | `malformedJSON`, `wrongType`, `missingField`, `unknownField`, `emptyText`, `unsupportedSchema`, `unsupportedSchemaVersion` |
| Vocabulary | `treesMismatch`, `unknownTree`, `sameSecondaryTree`, `unknownCapability`, `duplicateCapability`, `undeclaredCapability` |
| Cards | `noCards`, `duplicateID`, `retiredIDIsLive`, `duplicateRetiredID`, `tierListTooShort`, `tierOneGate`, `tierNamesIncomplete` |
| The join with native code | `missingBehavior`, `tierCountMismatch`, `unboundBehavior`, `duplicateBehaviorKey`, `secretScheduleMismatch`, `nativeIDMissing` |
| Synergies | `synergyTreeNotColoured`, `synergyLadderMismatch`, `missingSynergyBehavior`, `unboundSynergyBehavior` |

Three properties worth knowing:

- **The loader reports problems together.** It keeps reading after a problem where that is safe; only an unreadable document or a wrong schema stops it at once.
- **One broken card is reported once.** What an entry states (its id, its behaviour key) is recorded even when the entry fails elsewhere, so an empty face is not also reported as a missing id or an unbound behaviour.
- **Flags and numbers are typed strictly.** `"signature": 1` and `"schemaVersion": "1"` are errors.

A sample of the output for a file with three independent problems:

```
Ability catalog failed to load: 3 problems. First: emptyText at $.cards[32] "neutral_1".face.
  [emptyText] $.cards[32] "neutral_1".face: `face` is empty. Write the text, or remove the key if it is optional.
  [synergyLadderMismatch] $.synergies (fire): Tree `fire` lists thresholds [3, 4, 7]; it must list exactly [3, 5, 7], in that order (the native trigger rule fires at those counts).
  [duplicateID] $.cards[34] "neutral_3": `neutral_3` is already used by cards[33]. Card ids are permanent and unique (saves store them).
```

**Left for J2, as ruled:** where the file is read from in the app, when the load happens, and what a release build shows on failure.

## 6. Deviations from the J0 plan

1. **`AbilityCatalogSource.swift` is deferred to J2.** J0 listed the bundle lookup under J1. Nothing in J1 can call or test it while the runtime path stays unchanged, so it would have been untested dead code. The harnesses read the file by path.
2. **Rejection cases are generated, not stored.** J0 proposed one fixture file per error. The harness breaks the real authored file in memory instead, one edit per case, so the cases cannot go stale when the catalog changes.
3. **The J group is switched off for older mutants.** The J checks compare JSON with the legacy pool, so almost any edit to the pool fails them. Counting that as a kill would have let every older pool mutant pass without its own check. For any mutant not named `J1-`, `mutations.py` now runs the harness with `SPARKFORGE_SKIP_J=1` (the J group does not run) and ignores any JF / JL / JP line besides. This also keeps the suite's run time where it was.
4. **A defect in my own first J1 run, found and fixed.** The first run of the 56 J1 mutants reported 56 killed, but check JF2 had failed in every mutated copy, including ones that never touch the legacy code. Cause: the suite runs harnesses in parallel, the real `CodexManager` writes to the process's `UserDefaults` domain, and every harness process shared one domain, so each run's recorded Codex state was polluted by its neighbours. No mutant had been killed by JF2 alone, but the number was not trustworthy as reported. Fix: `run.sh` now gives each run one of 32 slots and names its executable after the slot, so parallel runs never share a domain; at most 32 small preference files exist (`sparkforge-catalog-harness-slotN.plist`), reused from then on. Twenty-four runs in parallel then passed all 141 checks, and the whole suite was re-run (section 5). **The independent review (Oct 6) found that the first slot scheme, which reclaimed a slot by checking whether the pid in it was alive, let two reclaimers take the same slot and let one delete another live run's fresh claim. It was replaced on Oct 6 by an exclusive `flock` held for the run (`tools/catalog-harness/with-slot.py`): ownership is the lock itself, nothing is reclaimed by inspection, and no run can remove another's. The repair, its reproduction and its evidence are in `docs/v2.2-catalog-j1-slot-repair.md`.** (An even earlier attempt named the domain after the process id and deleted its file on exit; the system writes that file after the process ends, so the delete lost the race and left hundreds of empty files in `~/Library/Preferences`, which were removed.) The same sharing existed before J1 for the older Codex checks (PB, CT); they are short enough that it had not shown.
5. **A correction to J0.** J0 said `checkBuildHint` names five more card ids. It names eight, across five hints. The J0 packet is corrected in place.
6. **Fewer recorded runs than J0 proposed.** J0's parity strategy spoke of "a few hundred seeded whole-run acquisition sequences". The run fixture holds **22 runs** (26 segments, 2,360 level-ups, 2,465 picks), chosen so that every one of the 148 card tiers is acquired and all 21 synergy tiers fire, with Panda taken to tier 5 in five runs and four runs continuing after `reset()`. The reduction was for fixture size (580 KB compact) and run time; the 444 per-tier deltas from three states and the 51 scenarios carry the combination coverage J0 wanted from volume. This is a deviation from the J0 plan; **Brandon accepted it on Oct 7** ("the 22 recorded runs alongside the per-tier and targeted-scenario coverage"), with the instruction not to expand the fixture volume solely to reach "a few hundred" and to preserve the fixtures for J2.

Items 1, 2, 3 and 6 are deferrals, substitutions or reductions against the accepted J0 plan. **Brandon accepted them on Oct 7** (verbatim: "the 22 recorded runs alongside the per-tier and targeted-scenario coverage; generated rejection cases; the mutation attribution filter; and the bundle-source/startup deferrals to J2"), with the instruction not to expand the fixture volume solely to reach "a few hundred" and to preserve the existing fixtures for J2, where the real JSON-backed manager must reproduce drafting, acquisition, reset, synergy bookkeeping and Codex behaviour. Items 4 and 5 are records, not requests.

## 7. Coverage limits

In order of weight.

1. **The real draft has not run over the JSON catalog.** `UpgradeManager` builds its own pool and offers no way to hand it another without changing the file, which J1 may not do. What stands in: JP1 and JP2 show the draft's only inputs (the cards' fields and their order) are identical, and the transcripts are recorded for J2 to replay through the real manager.
2. **Synergy bookkeeping and Codex writes are recorded, not yet exercised on the new path.** JP6's replay applies a synergy tier when a tree's count of distinct cards reaches 3, 5 or 7, counted from the JSON's trees, and requires that to match what legacy fired. The real once-per-run guard and the real Codex write over the JSON catalog are J2.
3. **Twelve config blocks in the harness are hand mirrors.** `Fire`, `Bleed`, `Everglow`, `IronMaiden`, `PolarVortex`, `Skybeam`, `Player`, `LevelUp`, `Projectile`, `Apex`, `DamagePipeline` and `ForgePath` come from the shared stubs, not from `GameConfig.swift`. Both sides of every comparison read the same values, and the source comparison covers which symbol is read, but the recorded numbers for those blocks are not evidence about the shipped values. Retiring the mirrors is test-tooling cleanup, which the kickoff keeps out of scope.
4. **Scene effects keyed by card id are not executed.** The harness does not compile `GameScene`. JP7 proves only that the ids the scene names exist.
5. **Nothing reads the bundled file.** It is in both built apps and identical to the authored file; loading it at runtime is J2.
6. **Duplicate keys inside one JSON object are not detected.** `JSONSerialization` keeps the last and says nothing. A small lint in the harness gate would close this; recommended for J2.
7. **Two synergy tiers firing on one pick.** Legacy applies them in dictionary order, which Swift does not fix. The fixtures record them sorted and the replay applies them sorted. Six recorded picks fire two at once and all replay to the recorded state on legacy itself, so no order dependence showed, but the order is not pinned.
8. **Build hints are outside the fixtures.** They stay native and unchanged in J2; when two trees reach two cards on the same pick, which hint shows also depends on dictionary order.
9. **What the mutants do not cover.** The 56 J1 mutants sample the registry (17 edits, against 169 closures), the JSON (16 edits), the loader (18 rules) and the parity kit (5); they show the checks have teeth, not that every possible wrong edit is caught. The exhaustive guarantees come from the checks themselves: JP4 compares every tier of every card, and the source comparison every closure.

- `EffectSource.legacy()`, checks JF1's source-digest clause and JF2, and the legacy control in JP6 (the fixtures become the only record of legacy).

- The "J1 STATUS" notes at the top of `AbilityCatalog.swift` and `AbilityBehaviors.swift`.

And add: the bundle source, the eager load, the failure presentation ruled in D1, the duplicate-key lint, and the replay of `legacy-run-transcripts.json` through the real manager.
