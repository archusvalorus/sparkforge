## Runtime change

One main-actor coordinator updates UMP, completes required forms, re-reads actual ATT status, requests ATT only if undetermined, and initializes MobileAds only after both gates resolve. An unresolved ATT completion remains closed and can retry on a later readiness event. UMP update/form failures do not create local permission: only the SDK's current `canRequestAds` may permit its documented existing-consent fallback. This is recorded separately from successful refresh.

All six rewarded placements share a weak-owner/placement queue, one in-flight load per placement and generation/token checks. Privacy changes invalidate caches and in-flight callbacks; cached presentation also rechecks the gate and presenter. Remove Ads benefits and exactly-once earned rewards remain intact. Dismiss/failure callbacks wake pending reloads. Required UMP privacy choices are reachable in existing Settings without replacing the device's ATT permission.

Native testing exposed the startup lifecycle problem: view appearance/activation callbacks could run while UIKit still reported inactive, and this legacy storyboard build could not rely on scene callbacks alone. Both app/scene activation paths and visible-root readiness defer their check to the next main-queue turn, then recheck actual state. No launch timer or unconditional SDK initialization is used.
