## 2. The defect, reproduced

The reviewer's probe (`probe-held-slots.py`) runs the runner's slot-allocation prelude 16 times at once against a slot directory that already holds slot 0 with a dead owner's pid, and keeps every acquirer alive until released. On the unrepaired runner, four rounds gave:

| Round | Live processes holding slot 0 at once | Processes that died during acquisition |
|---|---|---|
| 0 | 1 | 0 |
| 1 | **3** | 0 |
| 2 | 1 | **1** (`rm: … Directory not empty`) |
| 3 | **2** | **1** (`pid: No such file or directory`) |

(`repair/held-probe-before-repair.json`; the reviewer's own run showed the same shape.) Cause: reclamation was "read the pid file, `kill -0`, `rm -rf` the slot, `mkdir` it again, write my pid". Two reclaimers could both read the same dead pid; the slower one's `rm -rf` then deleted the faster one's freshly made, live claim, and both ended up owning the slot. The window between `mkdir` and writing the pid also left a claim with no owner information at all. A pid check is not ownership.

## 3. The repair (minimal diff)

Two files in the repository; nothing else changed.

**New: `tools/catalog-harness/with-slot.py`** (≈70 lines). Runs a command as the holder of one of N slots. Ownership is an **exclusive `flock` on the slot's lock file, held for as long as the command runs**: the wrapper takes it non-blocking, then runs the harness with the lock's descriptor inherited, so the slot stays owned if the wrapper dies before the child. The kernel releases the lock when the last holder exits, however it exits. Consequences:

- no pid file, no liveness guess, no reclamation step: a slot is free exactly when its lock can be taken;
- a live owner's slot cannot be taken, deleted or reused by anyone, including during acquisition (there is no acquisition window: the lock is held before the slot name is ever used);
- nothing is ever deleted: the slot directory holds only the 32 lock files; cleanup of each run is bounded to its own build directory, as before;
- when all slots are held, a newcomer waits (default 120 s, the suite never needs it) and then fails loudly; it never takes one.

**Changed: `tools/catalog-harness/run.sh`** (+24/−3). The pid-based prelude is gone; the binary is compiled under a neutral name and run through `with-slot.py`, which copies it to `sparkforge-catalog-harness-{slot}` and executes it. The three modes (`--dump`, `--record-parity`, the checks) are unchanged in behaviour. Diff: `repair/run.sh.diff`.

**Documentation:** `tools/catalog-harness/README.md` (the slot note), the J1 return packet (status line; section 6 item 4; a new item 6, see section 7 below) and this file.

**Not changed:** the authored catalog, the loader, the behaviour registry, the parity kit and fixtures, `mutations.py`, every shipped source file (byte-identical to HEAD), and every file Brandon owns.

## 9. Retained-test cleanup repair (second review, Oct 7) — cleanup-only packet

**Scope.** The second review passed the runner-lock repair (independent simultaneous and lifecycle probes, three parallel baselines, 9 of 9 independent mutants with intended attribution, the full-suite audit) and failed only the J1 closeout on one point: the retained test `slot-lock-test.py` could leave its own children alive and delete held lock files when a holder failed to start partway. This section repairs that test and nothing else. `with-slot.py`, `run.sh`, `mutations.py`, `main.swift`, the catalog, the loader, the registry and the fixtures are untouched, so no mutation evidence is affected and the full suite was not re-run.

**The defect, reproduced** (`rereview-oct7/repair2/leak-repro-before.json`, the reviewer's probe pointed at the working-tree test): three holders start, their children are stopped (SIGSTOP), the fourth start raises. The retained test's `finally` killed the three wrappers (reaped: true), then removed its temporary directory — but all three children were still alive afterwards, still holding exclusive locks on the three now-unlinked lock files (link count 0). Cause: the child pids were collected into a local list only after the whole list comprehension of starts had completed, so an exception mid-startup left the cleanup with nothing to kill; and the wrappers' deaths did not end their children, which had inherited the lock.

**The repair (one file: `tools/catalog-harness/slot-lock-test.py`).**

- *Ownership from the moment of spawn.* Every wrapper starts in its own process group (`start_new_session`) and is appended to its `Holders` before anything else happens; each `Holders` is registered for cleanup the moment it is made. Cleanup therefore owns every descendant even when a start stops halfway, before any pid line was read.
- *Bounded startup reads.* The child's report line is read with `select` under `STEP_TIMEOUT`; a holder that does not report in time is an error, never a hang.
- *Kill and reap before removing anything.* `cleanup()` sends SIGKILL to every owned process group (which ends stopped processes too, so paused children need no SIGCONT), waits for every wrapper, then polls until no owned group and no reported child remains, and returns whatever survived (the test requires nothing). The `finally` runs this for every `Holders` inside the temporary-directory context, so the directory is removed only after everything it started is gone.
- *Coverage added.* `pausedChildren` (four holders, children stopped, cleanup must kill, reap and release their locks) and `interruptedStartup` (three holders started with their children stopped, the fourth start raises, cleanup must leave no process and every lock free, with the lock files still present); plus `finalCleanup` (the `finally` reports no survivor).

## 10. Retained-test unconfirmed-cleanup repair (third review, Oct 7) — corrected packet

**Scope.** The third review passed everything in section 9 (the leak reproduction, the silent-startup bound, the normal path, the approval wording, the preserved checkout and the applicability of the 536/536 evidence) and failed one path: when the retained test's cleanup could not be confirmed, it still removed its temporary directory. **The defect, reproduced** (`cleanup-review/probe-unconfirmed-cleanup.py`, the reviewer's probe, run against the working tree before the fix: its own `unconfirmed-cleanup.json` of the review). Three holders start with their children stopped and holding locks, the fourth start is interrupted, and the cleanup's termination is made either to not complete or to raise. In both cases the test removed the directory while three locked children were alive: lock files unlinked (link count 0) but still held.

**The repair (one file: `tools/catalog-harness/slot-lock-test.py`; exact delta `rereview-oct7/repair3/slot-lock-test.diff`, the previous version reconstructed and verified against the `7675de59…` manifest).**

- *Deletion only on confirmed cleanup.* The directory is made with `mkdtemp`, not `TemporaryDirectory`, so no context manager or finalizer can remove it later. In `finally`, every owned `Holders` gets its bounded cleanup attempt (an exception in one does not stop the others); the directory is removed only when no survivor was reported and no cleanup step raised.
- *Otherwise it is kept and reported.* Incomplete termination and cleanup exceptions both keep the directory and its lock files, mark `finalCleanup.nothingSurvives` false (so the test exits unsuccessfully, or the original exception propagates), and report on stderr the kept path, the survivors, the errors, and what is known about the owned processes (wrapper pids with exit status and group liveness, child pids with liveness, and a bounded `ps` listing).
- *Bounded.* Cleanup attempts keep their `STEP_TIMEOUT` bounds; the diagnostics' `ps` call has a 5 s bound and can never itself fail the report.
