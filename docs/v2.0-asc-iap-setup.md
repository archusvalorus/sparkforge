### Do NOT mark any of these as a Promoted IAP

Promotion surfaces the item on the App Store product page, which leaks the
Panda secret tree before a player has found it.

**DECIDED Jul 27 — do not relitigate.** The App Store product page can *also*
auto-list top in-app purchases by display name, independent of promotion, so
the name "Flame Panda" may surface regardless. Brandon's call: **ship as-is
with the real display name.** A `???`-style masked display name risks an ASC
review question over a cosmetic surprise, and that trade isn't worth it.
Keep the not-Promoted setting; accept the residual leak.

## Local testing (no ASC round-trip needed)

`Sparkforge/Sparkforge.storekit` now exists, so purchases can be exercised in
the simulator before any of the above is live.

**One-time wiring (Xcode UI):**

Product → Scheme → Edit Scheme → **Run** → **Options** →
**StoreKit Configuration** → `Sparkforge.storekit`

Then premium skin chips will show real prices and buy flows will complete
against the local config.

### Why that step is manual (it can't be automated away)

Two separate things, and only one of them is a file we control:

1. **The `.storekit` file** — a fake storefront for the debugger. It is
   *already* the native Apple format: byte-for-byte what Xcode's
   File → New → StoreKit Configuration File emits, same JSON schema, same
   `"version": {"major": 4}` block. Open it in Xcode and you get the normal
   table-based StoreKit editor, not raw JSON. Nothing bespoke here, and
   nothing "auto-generates" — Xcode writes this file once and then you edit it.
2. **The scheme** — the thing that says *use that storefront when you hit Run.*
   This project has no shared scheme; Xcode auto-creates a per-user one under
   `Sparkforge.xcodeproj/xcuserdata/`, which git doesn't track. So the pointer
   has nowhere to live in version control.

Creating the file via Xcode's menu instead of by hand would **not** skip the
scheme step — that step exists either way. The only way to make it durable is
to mark the scheme **Shared** (Manage Schemes → ✓ Shared), which writes
`xcshareddata/xcschemes/Sparkforge.xcscheme` into the repo with the StoreKit
pointer baked in. Worth doing if there's ever a second machine or CI; for one
solo machine the single click is cheaper. Not done — deliberately, to avoid
scope creep during ship prep.

**One caveat:** the file is excluded from the target (a `membershipExceptions`
entry beside `Info.plist`), so it never ships in the bundle. Confirmed against
the built `.app`. Don't "fix" this by adding it to the target.

Remove Ads is listed at **$4.99**, matching ASC (Brandon confirmed Jul 27).
Note that every price the app *displays* is pulled live from StoreKit —
`removeAdsDisplayPrice()` and `loadSkinPremiumPrices()` both read
`Product.displayPrice`, and the UI deliberately shows no number at all rather
than a wrong one when StoreKit hasn't answered. So this value only affects what
the simulator shows; ASC remains the single source of truth in production.

**Reset local purchases between tests:** Xcode → Debug → StoreKit → Manage
Transactions → delete. `verifyPurchases()` runs on launch, so a stale local
entitlement will keep a skin unlocked and quietly invalidate a test.

## Verified already present

- **Restore Purchases** exists (Apple requires it) — `IAPManager.restorePurchases()`.
- Entitlements are generic: `ownedProductIDs` + `isPurchased(_:)` handle any
  non-consumable, so these three need no new plumbing.
- `Transaction.updates` listener and launch-time `currentEntitlements` sweep
  both route through `recordEntitlement`, so a purchase made on another device
  restores without a manual tap.
