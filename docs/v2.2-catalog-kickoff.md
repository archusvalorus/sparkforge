## Recommended architecture to validate in J0

1. **Versioned, ordered JSON definitions:** stable card IDs, tags, names/copy, tier metadata, signature/capstone/secret flags, existing positive and negative capability gates, retired IDs and synergy definitions. Use portable keys; explicitly map them to Swift enums. Preserve catalog order because ordering can affect seeded drafts.
2. **Typed Swift behavior registry:** JSON definitions bind to existing native effects by stable, validated keys. Keep closures, combat logic, timers, scene behavior and complex interactions in Swift. Validate effect bindings and tier counts rather than assuming metadata equality proves behavior equality.
3. **Explicit tuning ownership:** inventory config references, literals and generated numeric descriptions. Define one owner for each migrated field. Keep existing GameConfig ownership initially; do not create an independently authored duplicate in JSON or hard-code a current interpolated value without an update path. Identify any exception that needs a decision.
4. **Shared consumers:** the app, canon generator and local Atlas should read the same authored definitions after cutover. Keep supporting narrative/sidecar ownership explicit. Determine what a public H&H consumer needs from repository evidence; implementation in another repository or publication is a separate handoff.
5. **One authority after cutover:** a legacy snapshot is a parity fixture, not a second editable catalog. Do not leave competing Swift/JSON definitions indefinitely. Invalid catalog data must be diagnosed; it must not silently omit cards or fabricate defaults. Propose the precise startup/failure policy before production cutover.

This makes content additions using existing behavior cheaper. New mechanics still require native implementation, tuning and tests; a future platform port still needs its own effect implementations. No universal effect language, remote content delivery, platform-port implementation or combat-engine rewrite belongs in this migration.
